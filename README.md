# 峡谷有数 · KPL Insight

**峡谷有数是一个面向 KPL 观众的赛事数据分析项目。** 从查询赛程、战队和选手表现，到查看比赛中的胜率变化、模拟系列赛结果，希望让比赛数据不只停留在赛后统计，而成为理解比赛的另一种方式。

项目起于我在 **2024 年对 KPL 数据分析和比赛预测的探索**。从研究赛事页面与接口、编写采集脚本开始，逐步加入数据整理、预测模型、比赛复盘和网站展示，形成现在的峡谷有数。2024 年是早期探索阶段，并不代表现在的网站和全部功能在当时已经完成。

你可以直接打开网站，查一场比赛、比较两支队伍，或者研究一名选手在不同英雄上的表现。想了解实现过程，也可以继续阅读接口采集、特征构建、模型训练、校准与评估的说明。

欢迎直接使用峡谷有数，也欢迎借助 AI 在现有项目上扩展自己需要的功能。如果觉得新功能对其他人也有帮助，可以提交 PR，一起完善项目。

## 这个项目想解决什么问题

看比赛时，我们通常能很快知道比分，但想进一步理解比赛，还会遇到一些具体问题：

- **比赛进行到这里，谁更有机会赢？** 经济领先、推塔、资源和战队历史表现，如何一起转成胜率估算？
- **一场比赛是怎样改变局势的？** 终局统计给出结果，时间序列才能帮助找到变化发生的时段。
- **某位选手的一场表现到底如何？** 不同位置、不同英雄承担的任务不同，需要合适的参照。
- **一支队伍怎样选择阵容？** 单场选禁、系列赛已用英雄和长期 BP 倾向，需要放在各自的样本范围内看。
- **一场 BO7 可能打成什么比分？** 单局胜率和整个系列赛的比分分布，是两个相互关联的问题。
- **分析结果能否核对？** 一句结论应当能回到具体比赛、数据范围和方法说明。

峡谷有数围绕这些问题，将采集、整理、建模和展示连接起来。你可以只使用查询功能，也可以继续深入分析与模型部分。

## 值得关注的设计

- **从一场比赛继续查下去。** 赛程、战队、选手、英雄与单局详情相互关联，汇总统计可以回到具体对局查看。
- **不只看结果，也看过程。** 在有分钟快照的比赛中，把经济、资源和胜率放在同一条时间轴上，帮助找到值得回看录像的时段。
- **用合适的参照理解表现。** 选手 × 英雄分析提供同位置、同英雄的分位数参照，减少只看总量、忽略位置职责的误读。
- **把单局和系列赛分开研究。** 局内胜率、BO7 比分模拟、逐手 BP 回放和战队长期选禁风格，分别回答不同层次的问题。
- **让分析有据可查。** 保留原始响应、数据覆盖说明与结构化报告，区分比赛事实、模型估算和仍需验证的判断。

这些设计共同构成项目的特点：不仅提供一个预测数字，也把数字背后的比赛、数据和方法连接起来。

## 主要功能

下面按使用场景介绍功能。普通观众可以直接使用网站；采集、训练和批量生成报告等开发工具需要在本地运行，相关步骤见“开始使用”。

### 1. 赛事查询与历史归档

**想找一场比赛，先从赛程进入。** 按赛事、赛季和日期查看对阵、比分与系列赛进程，再进入每一小局。这样既能快速知道“谁赢了”，也能继续查看“每局怎么打”。

<details>
<summary><strong>展开功能说明、操作步骤与截图</strong></summary>

- **赛程层**：查看哪一天、哪项赛事、哪两支队伍交手，以及大场结果。
- **系列赛层**：查看各局胜负、阵容与已有回放入口，区分大场比分和单局结果。
- **单局层**：查看有记录的选手、英雄、BP 与赛后统计；有过程快照时可以继续复盘。
- **历史层**：通过年份和赛事范围查询旧比赛。不同年代的数据完整度不同，具体覆盖见“数据覆盖与更新说明”。

例如，想研究两队的一次 BO7，可以先找到大场，再逐局查看阵容和胜方，而不用在不同统计页面之间重新搜索。

比赛、单局和赛事分别使用自己的标识进行关联。跨层展示时按实际战队身份对齐，处理大场对阵顺序与单局蓝红方不同的情况。

[![赛程查询：按赛事与日期查找对阵，再进入系列赛和单局](docs/images/schedule-current.jpg)](https://hccccc01333.github.io/KPLdata-site/schedule.html)

*赛程查询是比赛详情、BP 和复盘的共同入口。上图为先前留存的已部署站点截图。*

入口：[赛程与比分](https://hccccc01333.github.io/KPLdata-site/schedule.html)。

</details>

### 2. 单局胜率估算

**运行方式：本地启动采集与预测；在线网页展示已发布记录。** 实时模型不是浏览器内直接运行的公共服务，关闭本地程序后就不再持续取得新的预测。

**回答“比赛打到这一刻，哪一方更有机会获胜”。** 在取得比赛进行中的快照后，结合经济、击杀、推塔、资源、选手位置数据和历史先验，输出当前局面的获胜概率。

<details>
<summary><strong>展开功能说明、操作步骤与截图</strong></summary>

一条预测的处理过程是：

1. 读取当前快照，确认对局、时间和双方战队。
2. 计算经济差、资源差、局势变化与分路相关特征。
3. 根据比赛阶段调用模型，完成阶段混合、概率校准与输出检查。
4. 保存预测及相应时间信息，供后续复盘和核对。

当前 V12 使用早期与中后期分阶段模型、概率校准和经济一致性护栏。与只看终局胜负不同，这条链路需要持续获取过程数据；比赛日实时能力依赖采集程序实际运行。

胜率由统计学习模型计算，AI 编程助手则用于辅助代码开发。这里的 70% 表示模型对当前局面的概率估算，而不是这一场必胜。训练流程、真实样本与辅助样本的区别、概率评估方式见后文及[模型说明](docs/model-card.md)。

</details>

### 3. 分钟时间轴复盘

**把整场比赛拆成可以来回查看的时刻。** 对有分钟快照的比赛，可以切换单局、拖动时间轴，同时对照胜率、经济、击杀、防御塔、资源与选手面板，找到值得回看录像的时段。

<details>
<summary><strong>展开功能说明、操作步骤与截图</strong></summary>

建议这样使用：

1. 先看单局结果和页面给出的事实摘要，确认双方身份。
2. 展开完整时间轴，拖到自己感兴趣的分钟。
3. 对照前后经济、资源和曲线变化，定位变化窗口。
4. 结合原始录像判断具体操作与战术，不把统计变化直接当成原因。

系统分别保留**比赛当时保存的预测**和**当前模型基于历史快照重新计算的结果**。模型版本、数据完整度和采集延迟都可能使两者不同，页面及报告应按各自口径理解。

[![分钟复盘：展开时间轴，同步查看经济、资源与胜率](docs/images/replay-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/match.html?id=2026062603&g=3&m=13)

*本地版本实拍。时间轴只适用于有过程快照的对局；查到赛果不等于拥有完整过程。模型判断与最终结果不一致时，也应保留并检查，而不是隐藏。*

</details>

### 4. 赛前大场模拟与胜率沙盘

这两个工具分别回答“开赛前可能打成什么比分”和“比赛中这种局面通常怎样发展”，不混用同一种概率。

<details>
<summary><strong>展开功能说明、操作步骤与截图</strong></summary>

#### 赛前大场模拟：从单局胜率到整场比分

选择两支队伍及 BO3、BO5、BO7 赛制，查看大场获胜概率、最可能比分、打满概率和完整比分分布。也可以手动设定单局胜率，观察同样的实力差在不同赛制下如何影响结果。

当前网站以历史 Elo 实力评级作为赛前概率基础，并按赛季滚动校准概率幅度；近期状态、历史交手等作为赛前情报展示。页面还提供走步回测、方法说明和可展开的逐局概率树。

**早期决赛预测探索使用过 BO7 蒙特卡洛模拟；当前网站按系列赛状态逐局展开，精确计算比分分布。** 两者属于不同阶段的实现，不能把早期方法名称直接当成当前网页算法。当前计算假设各局独立，不模拟临场手感延续或实际 BP 博弈。

[![赛前模拟：选择战队和赛制，查看大场胜率与完整比分分布](docs/images/simulator-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/simulator.html)

*本地版本实拍。大场胜率、单局胜率和某个具体比分的概率是不同指标，页面分别展示。*

#### 胜率沙盘：把模型判断与相似历史局面对照

选择一场比赛和某一分钟，查看当前局势、模型判断，以及相似历史对局最终的结果。页面支持切换历史结果与模型视角，并提供翻盘局、明显优势局等探索入口。

进阶功能允许调整经济差、击杀等输入，观察模型输出变化；模型体检部分则展示不同阶段的表现、校准与薄弱场景。这种条件探索用于理解模型，不意味着实战只改变一个指标就能获得同样结果。

[![胜率沙盘：沿时间轴查看模型判断，并与相似历史状态对照](docs/images/sandbox-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/sandbox.html)

*本地版本实拍。相似状态的历史获胜比例是样本统计，模型胜率是估算，两者可对照但不互相替代。*

入口：[大场模拟](https://hccccc01333.github.io/KPLdata-site/simulator.html) · [胜率沙盘](https://hccccc01333.github.io/KPLdata-site/sandbox.html)。

</details>

### 5. 战队、选手与英雄分析

从战队概况、选手资料和英雄环境逐步深入，最后回到同位置、同英雄的具体比赛表现。

<details>
<summary><strong>展开功能说明、操作步骤与截图</strong></summary>

#### 战队：从整体表现回到具体对局

查看战队表现、交手记录与相关比赛，再继续进入选手、英雄和 BP。适合研究同一队伍在不同赛事范围内的表现，也适合为一场对阵补充背景资料。

[![战队档案：从战队表现继续查看相关比赛与统计](docs/images/team-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/teams.html)

*本地版本实拍。统计与所选数据范围关联，比较时需要先确认年份、赛事和样本量。*

#### 选手：不仅有排行，也能看英雄池和比赛记录

从选手资料进入位置表现、英雄使用和历史对局。选手对比页将多名选手放在同一张雷达图与指标表中；雷达默认按同位置分位归一化，表格仍保留原始统计，避免把不同职责简单换成一个总排名。

[![选手资料：查看英雄使用和历史比赛](docs/images/player-current.jpg)](https://hccccc01333.github.io/KPLdata-site/players.html)

*先前留存的已部署站点截图。选手资料提供从名字进入比赛记录的路径。*

[![选手对比：雷达图与原始统计结合，并标明同位置参照](docs/images/compare-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/compare-player.html)

*本地版本实拍。跨位置比较时应区分位置内分位和原始指标，输出更高不直接等于表现更好。*

#### 英雄：查看选用情况，再理解谁在使用

英雄页面提供使用、选禁和样本范围，帮助观察指定赛事中的英雄环境。英雄胜率需要连同出场量、使用战队和赛事范围一起理解，小样本高胜率不直接代表英雄强弱。

[![英雄数据：结合出场、选禁和样本范围查看英雄表现](docs/images/heroes-current.jpg)](https://hccccc01333.github.io/KPLdata-site/heroes.html)

*先前留存的已部署站点截图。英雄汇总与选手个人英雄表现是不同观察角度。*

#### 选手 × 英雄：按系列赛展开，并提供同类参照

这是进一步研究个人表现的工作台：选择选手、赛事和英雄，查看出场、胜负、KDA、每分钟伤害、每分钟经济、参团率与死亡频率，再进入系列赛证据。

工作台提供**同位置、同英雄的 P50 / P75 / P90 参照**，分别表示相应样本中约第 50%、75%、90% 位置的水平。参照池不足时会扩大并标注范围，仍不足则停止评级；死亡频率等指标还需要区分“高更好”或“低更好”。

例如，想知道某位发育路选手的公孙离表现，可以先看使用样本，再看同位置同英雄的伤害与经济参照，最后回到具体系列赛，而不是只依据一次 0% 或 100% 胜率下结论。

[![选手与英雄工作台：英雄列表、分位参照和系列赛证据联动](docs/images/hero-performance-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/hero-performance.html?player=一诺)

*本地版本实拍。左侧选择英雄，右侧展示指标参照、样本范围与比赛证据；分位数是描述性统计，不是官方选手评级。*

入口：[战队](https://hccccc01333.github.io/KPLdata-site/teams.html) · [选手](https://hccccc01333.github.io/KPLdata-site/players.html) · [英雄](https://hccccc01333.github.io/KPLdata-site/heroes.html) · [选手 × 英雄](https://hccccc01333.github.io/KPLdata-site/hero-performance.html)。

</details>

### 6. BP 回放、战队风格与教练档案

既能回看某一局的选禁，也能研究战队长期偏好与教练任期内的 BP 统计。

<details>
<summary><strong>展开功能说明、操作步骤与截图</strong></summary>

BP 指比赛中的英雄禁用与选择。这一部分分成“某一局怎么选”和“长期更偏好什么”两个层次。

#### BP 演播室：按顺序回看一局选禁

选择真实比赛与单局，在逐手回放和最终阵容之间切换，查看双方选禁、系列赛前几局已用英雄与本局赛后数据。已有顺序记录用于还原选禁过程，阵容卡片的展示位置不直接表示分路。

[![BP 演播室：真实比赛的最终阵容，并可切换逐手选禁回放](docs/images/bp-studio-20261027.jpg)](https://hccccc01333.github.io/KPLdata-site/bp-studio.html?id=2026102201&g=1)

*本地版本实拍，当前画面为最终阵容。逐手回放、前几局已用英雄和赛后统计在同页提供。*

#### 战队 BP 风格：把偏好、禁用和赛果拆开看

只使用双方各 5 选、5 禁的完整 20 手记录，展示常用英雄、选择集中度、英雄组合、己方禁用与对手禁用。

## 数据接口是怎样独立探索出来的

数据从哪里来，是整个项目的第一步。这里的采集主要是请求赛事页面使用的数据接口，读取结构化返回内容，再整理成后续分析能够使用的格式；历史补充集还涉及页面解析。

早期，我从官方赛事页面和浏览器里的网络请求入手，独立定位数据来源，逐项理解比赛、战队、选手和英雄字段，再编写采集脚本。随着需要回答的问题增多，单场数据获取逐步发展为比赛日监控、快照归档和分析流程。下面按这条链路说明具体做法。

### 从官方页面的网络请求找到数据来源

通过浏览器开发者工具的网络面板，查看赛事页面实际发出的请求，定位与赛程、对局有关的响应，再检查请求方法、参数、请求头和返回字段。找到候选接口后，用不同比赛的数据对照页面显示，核对比分、战队和选手等信息。

项目使用的对局接口路径之一为：

```text
https://prod.comp.smoba.qq.com/leaguesite/battle/open
```

请求单局数据时需要对应的 `battle_id`。接口地址、字段和返回行为可能变化，因此还需要在不同比赛和比赛状态下核对，确认采到的是哪一局、哪个时间点的数据。接口服务由数据提供方维护，本项目负责采集接入、字段解析和后续处理。

### 把返回数据整理成可分析的结构

返回数据包含比赛、双方战队、选手、英雄和 BP 等不同层级，不能直接当成一张扁平表使用。项目逐步整理出：

- 比赛和单局的标识、关联、状态、时长与胜负。
- 战队级经济、击杀、防御塔和大型资源。
- 选手、位置、英雄及经济、输出、承伤等字段。
- 英雄禁用与选择记录，以及可取得的回放信息。

需要进一步核对字段单位、空值、嵌套结构与不同赛事之间的差异。标识符通过接口记录和索引关联，不将未经验证的数字编码猜想作为采集依据。

### 从单场采集发展到比赛日监控

单场请求解决的是“现在能拿到什么”。实时胜率需要保存连续过程，因此采集链路还要处理：

1. 从赛程识别当前比赛及对应单局。
2. 在比赛进行时轮询接口，保存带时间信息的原始快照。
3. 将快照转成统一特征，再产生并保存预测。
4. 识别单局结束，继续跟踪后续比赛并归档结果。
5. 记录异常与缺失，避免把未取得的数据默认为零。

重试、采集间隔和状态判断都影响数据质量。接口返回历史终局时，只能得到它当前提供的状态，不能据此恢复整场真实的分钟过程。

### 保留原始记录，处理接口中的实际差异

采集后保留原始 JSON，便于重查字段、修复解析和追溯异常。后续扩展指标时，可以先检查已经保存的响应，减少重复请求。

一个具有代表性的问题是**跨局换边**：大场对阵顺序与单局阵营顺序可能不同。项目按单局实际战队身份解释胜方和胜率，再以逐局胜方汇总核对大场比分。

另一个问题是**终局摘要与过程帧不同**：系列赛分析会检查击杀、推塔、资源等累计计数是否回退，并对异常帧进行处理。相关案例和校验逻辑是数据产品的一部分。

从定位请求到形成可用数据，主要工作落在字段理解、比赛身份对齐、持续采集与异常处理上。相关实现入口列在下方“仓库与开发文档”中，历史补充数据和软件依赖的来源见“项目贡献与第三方来源”。

## 模型与分析为什么这样设计

### 比赛的不同阶段，可用信息不同

开局和后期的经济、资源与推塔含义不同。V12 采用早期随机森林专家与中后期多模型软投票，再通过分钟过渡混合与分阶段校准生成概率。

中后期候选模型包括逻辑回归、随机森林、极端随机树和梯度提升树。早期探索比较过 LR、SVM、随机森林、KNN 和 XGBoost；当前 V12 使用的是后续迭代形成的分阶段方案。

### 特征表达当前局面与已有历史

特征包括经济差及变化趋势、击杀与推塔差、资源控制、分路经济与贡献，以及只使用此前比赛构造的战队先验。

例如，同样领先一千经济，发生在第 3 分钟和第 20 分钟的含义不同；总经济相近时，经济分配和资源状态也可能不同。特征工程的作用，是把这些差异转换成模型可使用的输入。

部分“地图压力”“后期成长”等指标是根据统计字段推导的代理特征，不等于已经从视频识别出选手位置、技能或战术。

### 用概率评估约束模型

真实比赛按时间顺序、以整局为单位划分训练、校准和测试数据。同一局中相邻时点高度相关，不能随机分散到不同集合，再把高分当作泛化能力。

校准用于检查概率是否与实际结果相称。例如，许多被预测为 70% 的样本，实际获胜比例是否接近七成。Brier 等指标帮助衡量概率误差，不能只看判断胜负的准确率。

评估还要区分开局、中期、后期与翻盘局。多个快照不是多场独立比赛，相关报告需要同时说明**局数、时点数、时间范围与模型版本**。

### 真实快照与辅助样本分开解释

训练流程结合真实快照和由终局数据生成的辅助样本。辅助样本用于模型研究，不是重新发现的真实比赛过程；校准和测试需使用隔离的真实对局，并防止测试局通过辅助样本回流训练。

当前仍存在早期信息不足、翻盘局、跨版本变化和真实样本规模有限等问题。经济一致性护栏属于异常输出兜底，不能替代模型校准或独立评估。

更完整的方法、适用范围和限制见[模型说明](docs/model-card.md)。

网站读取预先构建的静态数据，打开即可浏览，无需在访问者的电脑上运行采集或训练。比赛日数据由独立的采集程序获取，经处理、导出与发布后供网站展示；页面内容以已发布的数据版本为准。

## 技术架构与技术栈

项目的数据生产、模型研究和网站访问并不是同一个进程。下面按职责拆成五张图，先看全景，再按需展开具体链路。图中展示的是模块与数据流，不表示所有步骤都已自动化。

### 1. 系统全景：数据、模型与产品如何连接

![系统全景：数据来源、采集归档、质量检查、建模、预测与网站展示](docs/images/architecture-overview.svg)

数据经过清洗后，一部分用于研究建模，一部分进入统计、报告和页面构建。比赛日预测加载已有模型；普通访问者只读取已发布的网站文件。

<details>
<summary><strong>2. 展开：比赛日采集与预测流程</strong></summary>

![比赛日采集与预测：识别单局、轮询接口、保留原始快照、统一特征并归档预测](docs/images/collection-flow.svg)

- **输入**：赛程与当前单局标识，以及接口实际返回的比赛状态。
- **核心处理**：按间隔采集，保存原始响应，统一战队身份与特征，再调用已有模型。
- **异常分支**：请求失败或暂时缺失时记录并重试，不将缺失值直接当成零。
- **输出**：原始快照、过程数据和带时间信息的预测记录；比赛结束后继续切局或归档。

这条链路解决“比赛进行时怎样留下过程”，不是从赛后一个终局响应推导出整场真实历史。

</details>

<details>
<summary><strong>3. 展开：模型训练、校准与独立评估流程</strong></summary>

![模型管线：真实比赛整局按时间隔离，分别进入训练、概率校准和冻结后的独立测试](docs/images/model-pipeline.svg)

- **训练**：在允许的训练区间构建特征，结合真实快照与合格训练局的辅助样本。
- **校准**：使用隔离的真实比赛，让输出概率与实际发生频率更相称。
- **测试**：冻结模型和校准配置后，在未参与拟合的真实比赛上评估。
- **记录**：同时报告比赛数、时点数、时间范围与版本，检查早期、后期和翻盘场景。

相邻分钟帧高度相关，因此以整局划分，而不是把同一局随机拆到不同集合。辅助样本也不能绕过比赛身份隔离。

</details>

<details>
<summary><strong>4. 展开：系列赛证据报告生成流程</strong></summary>

![系列赛报告：原始记录经过身份、比分与计数检查后，形成统一 JSON、Markdown 与网页展示](docs/images/series-evidence-flow.svg)

- **对齐**：先确认每局的真实战队和蓝红方，再核对大场比分。
- **检查**：识别缺帧、计数回退或输入冲突；按规则报错、隔离或降级。
- **生成**：提取检查点、候选变化窗口和分层结论，保存统一结构化报告。
- **消费**：命令行导出 Markdown，网站读取同一份 JSON；固定基准检查输出与降级行为。

报告提供证据与回看线索，不把模型变化直接解释成某个事件造成胜负。

</details>

<details>
<summary><strong>5. 展开：静态数据构建与网站发布流程</strong></summary>

![网站发布：数据工具产出经过构建和检查后发布，浏览器按需读取静态文件](docs/images/site-publishing-flow.svg)

- **本地生产**：采集、模型和分析工具产生快照、预测、统计与报告。
- **构建发布**：将展示文件接入独立网站仓，检查数据范围、隐私和许可，再发布托管版本。
- **浏览访问**：加载页面与静态数据，不在访问者电脑上自动运行爬虫和训练。
- **贡献迭代**：功能修改经本地验证、PR 审阅与后续发布后，才进入公开版本。

本地新功能、模型产物、体验包和在线网站可能处于不同版本，使用时需要看对应更新时间。

</details>

### 技术栈与各自职责

- **Python、Requests**：赛事请求、批量采集与比赛日监控。
- **pandas、NumPy**：嵌套数据整理、指标聚合、特征工程和数据导出。
- **scikit-learn、SciPy、joblib**：模型训练、概率校准、评估与模型产物保存。

- **GitHub Pages、GitHub Actions、Cloudflare Workers**：静态网站发布与托管。
- **Beautiful Soup**：当前历史补充集研究中使用的页面解析工具；具体工具与数据来源以相关模块为准。

项目分为数据与模型仓、静态站点仓。当前代码组织与运行方式不同，复现时应使用所在仓库对应的命令。

已安装 Git 和 Python 3 的用户，可以获取站点仓库并启动本地 HTTP 服务：

```bash
git clone https://github.com/hccccc01333/KPLdata-site.git
cd KPLdata-site
python -m http.server 8000 --bind 127.0.0.1
```

在浏览器打开 `http://127.0.0.1:8000/`，保持终端运行；结束时按 `Ctrl+C`。网页按需请求数据，请通过本地 HTTP 服务访问。

### 想看实时胜率：先在本地启动

以下命令在**数据与模型仓库**中运行，不是在静态网站仓库中运行。先完成下面的 Python 环境安装。

- **尚无模型**：使用 `monitor --collect-only` 仅采集真实过程，暂不输出胜率；积累合格数据后训练、校准与评估。
- **已有可信的有效模型**：启动比赛日监控，程序在本地采集快照并保存预测。公开源码不附带预训练权重，首次安装不能跳过数据准备直接获得实时胜率。

```bash
python -m kpl_insight monitor --league-id 20260004 --interval 3 --no-auto-train
```

`20260004` 是赛事 ID 示例，需按目标赛事调整。比赛未开赛、接口不可用或缺少有效模型时，不保证产生预测。运行期间保持终端和网络连接，停止时按 `Ctrl+C`。

可另开终端启动本地 Streamlit 工作台查看已有数据；**工作台不是采集程序的替代品**。若希望在线静态网站看到新结果，还需另行导出、接入站点并发布，运行监控不会自动替你部署。

## 用 AI 扩展你想要的功能

使用峡谷有数，不必只限于现有功能。如果你想增加一种筛选、一个对比视图，或者一项更符合自己看比赛习惯的分析，即使不熟悉编程，也可以尝试让 AI 编程助手在现有项目上帮助实现。

**你提出需求，AI 辅助写代码，你再用真实比赛核对结果。** 可以先在本地做一个自己用得顺手的版本；如果觉得这个功能也能帮助其他人，欢迎提交 PR（Pull Request，代码修改提案），一起完善项目。不需要先成为专业开发者，也不要求每次个人修改都提交。

### 从一个小功能开始

1. **说清楚想解决的问题。** 例如“想在选手页面同时比较两名选手使用同一英雄的表现”，明确筛选条件和希望看到的结果。
2. **让 AI 先阅读现有实现。** 页面功能从[网站仓库](https://github.com/hccccc01333/KPLdata-site)入手；采集、模型和分析逻辑从[数据与模型仓库](https://github.com/hccccc01333/kpl-insight)入手。先确认已有数据能否支持需求，再决定怎么改。
3. **在本地完成一个最小版本。** 一次只增加一个功能，尽量复用已有数据与组件，不让 AI 编造缺失字段或比赛记录。
4. **亲自检查结果。** 选择几场熟悉的比赛核对统计，检查筛选、空数据和手机显示；涉及计算逻辑时补充或运行相关测试。
5. **愿意分享时再提交 PR。** Fork 对应仓库（在自己的 GitHub 账号下创建副本），提交修改并发起 PR，说明用途、实现方法和验证结果。也可以先通过 Issue 交流想法，减少重复开发。

可以这样向 AI 描述需求：

```text
我正在使用峡谷有数，想在现有项目上增加［具体功能］，
用于解决［使用场景中的问题］，不是重新创建一个网站。

请先阅读项目 README 和相关代码，说明现有数据是否足够、
哪些文件需要修改；如果字段或统计口径不清楚，先向我确认，不要编造。

第一版只实现［最小范围］，复用已有页面风格与数据结构，
不改动无关功能，并处理空数据和手机显示。

完成后告诉我如何启动、核对结果和运行相关测试。
如果后续提交 PR，请帮我整理修改说明和验证步骤。
```

## 当前边界与后续工作

- **归档覆盖与过程覆盖不同。** 查到赛果不代表有分钟快照，缺失过程不会被补写成真实事件。
- **模型还需持续改进。** 早期局面、翻盘局、不同版本和有限真实样本，都会影响概率质量。
- **统计变化不等于因果。** 事件附近胜率变化不能直接证明它造成了输赢，教练与选手的意图也不能仅由统计推断。
- **视频解析仍在研究。** 第一视角的技能、轨迹与行为提取尚未完成真实验收，不作为稳定功能对外承诺。
- **发布范围有区别。** 完整采集快照和预训练权重不随公开源码分发；网页已有静态展示数据，训练复现需另行准备符合格式且有权使用的数据。

后续重点是补充真实过程样本、改进时间外评估与翻盘局分析、完善历史数据质量，并持续改善查询和复盘体验。
