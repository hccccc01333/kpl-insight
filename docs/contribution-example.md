# 贡献示例：给复盘时间轴增加逐帧按钮

> 以下以新增逐帧按钮为例，说明如何提出需求、借助 AI 实现、验证结果并准备 PR。它是贡献流程示例，不是现有功能说明。

## 1. 把感受写成可实现的需求

“手机上拖动时间轴不容易停在某一帧，希望增加‘上一采样点 / 下一采样点’按钮。”

第一版只处理已经加载的复盘帧，不新增数据接口，也不把相邻采样点误称为一秒间隔。

验收条件：

- 按钮在当前单局内移动一个真实采样点。
- 第一帧禁用“上一采样点”，最后一帧禁用“下一采样点”。
- 点击后滑块、时间、曲线指示和统计面板同步更新。
- 切换单局后边界状态正确，没有数据时不给出虚假的帧。
- 手机上容易点击，键盘可操作，并有明确按钮名称。
- 分享链接继续使用实际时点；不产生超过当前局范围的索引。

## 2. 找到应该修改的仓库与入口

这是网页交互，应先查看[网站仓库](https://github.com/hccccc01333/KPLdata-site)，而不是修改 Python 模型。

现有复盘逻辑位于 `assets/replay.js`，其中 `setFrame`、`paint` 与 `#rpRange` 负责选帧和更新。让 AI 先阅读它们，复用既有更新路径，而不是复制一套独立状态。

## 3. 可以交给 AI 的需求

```text
请先阅读峡谷有数网站 README、AGENTS.md（若有）及 assets/replay.js。
我想在现有复盘时间轴增加“上一采样点 / 下一采样点”按钮。

请先说明现有选帧与重绘逻辑，再给出最小修改方案。
复用既有状态，不增加数据接口，不编造缺失帧。
首尾正确禁用；切局、空数据、手机和键盘操作都需要处理。
不要改动概率算法、统计口径、其他页面或发布配置。

完成后列出修改文件、验证步骤与尚未验证的部分。
不要替我创建远程 PR、提交或部署。
```

AI 可以帮助写代码和定位问题，但使用者仍需要亲自核对功能是否符合需求。

## 4. 在本地验证

先按网站 README 启动 HTTP 服务，再测试：

1. 选有分钟快照的比赛，逐点前进和后退，比较滑块与面板。
2. 分别到第一帧、最后一帧，再连续点击，确认不越界。
3. 切到另一局，确认没有继承错误帧索引。
4. 试无快照、加载失败和手机宽度；检查控制台异常。
5. 用键盘 Tab 选中按钮并操作，核对名称与禁用状态。
6. 与原页面对照，确认概率与数据没有被无关改动。

涉及逻辑的改动应按对应仓库现有测试约定补充或运行测试。没有实际运行的检查标注“未验证”，不能让 AI 把清单全部自动写成通过。

## 5. 愿意分享时再提交 PR

Fork 对应仓库，在自己的副本中提交这一项修改，再向原仓发起 Pull Request。若范围较大，先通过 Issue 交流。数据、模型和网站分别选择正确仓库。

PR 描述可以这样写：

```text
标题：为复盘时间轴增加上一 / 下一采样点按钮

用途：
手机上更容易停在指定采样点，便于对照经济和资源。

实现：
复用现有选帧与绘图逻辑；首尾禁用；切局后更新边界。

验证：
填写实际跑过的比赛、浏览器、手机宽度与测试命令。
附操作前后截图或短演示，并列出尚未验证的情况。

范围：
不修改模型、统计口径、数据文件或部署配置。
不包含私人信息、密钥、权重和原始媒体。
```

提交时请将模板替换为实际用途、实现与验证记录。维护者会根据正确性、方向和维护成本评审。
